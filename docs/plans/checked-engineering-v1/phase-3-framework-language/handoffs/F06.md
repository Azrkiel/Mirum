## Migration and rollback

Tables are created `IF NOT EXISTS` on first construction of `RevisionStore`, and nothing existing is altered. Rollback is reverting the F06 commits. The three new tables can stay in an existing database unused: nothing else reads them and no foreign key points at them.

## Blockers and limitations

Interpretation choices (none changes a D decision):
- Compile errors (`MelError`) at `stage` propagate unchanged instead of being returned; nothing is written.
- A stale-parent or capacity refusal is decided before any compile or draft, so it writes nothing. A parent race lost at the final insert leaves an orphan draft, which expires under the existing draft retention.
- Restore rows store no payload: IR and source are read from the evidence revision.
- A staged revision with an `admit_intent` journal entry is failed `interrupted` on restart, even if the admit was refused in-process (for example `AdmissionBusy`).
- `rebuild` accepts any revision whose evidence payload is present. `compare` across two programs of the same client is allowed.
- There is no runtime wiring until F08: no `create_runtime`, `api_v1` or `main.py` change, and no route.
- The Windows host skips the native and posix tests; only the CI rows are native evidence.
