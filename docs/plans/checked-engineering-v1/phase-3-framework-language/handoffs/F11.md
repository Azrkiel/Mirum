# F11 native kernel feasibility

**The equipment-bay evidence supports a no-go decision for a new native solid-modeling kernel.** Keep OCCT as the analytic B-rep backend and qualify the existing PicoGK backend within its STL geometry-only capability. A new kernel investment would require a named unmet operation or a repeatable robustness, precision, throughput or deployment limit.

## Evidence

Measured six delivered AP214 assemblies on Linux x86-64 with CPython 3.12.14, CadQuery 2.7.0, cadquery-ocp 7.8.1.1.post1 and steputils 0.1. Files were 213–294 kB with 32–48 mounting pairs. The XDE reread took 126–165 ms per file. The separately implemented Part 21 evaluation took 112–235 ms. This was one warmed, sequential measurement per case excluding disk I/O and process startup. Both paths recovered the same nominal and shifted correspondences. FreeCAD 1.0.0 with OCCT 7.8.1 also received all six assemblies.

The PicoGK registry exposes STL and rejects STEP. The receiving-application replay and stable occurrence names use the OCCT path. The twelve-module finding exhausts the fixture's two allowed layouts and is a packaging constraint. Neither result establishes a defect in the solid geometry algorithms used for the bay.

## Reopen criteria

Reconsider only for a repeatable operation the qualified backend cannot deliver, or a measured constraint exceeding a product requirement. Pin analytical truth, accepted exchange geometry, representation and tolerances before prototyping. A bounded operator evaluation compares OCCT, the relevant PicoGK operation and a candidate implementation such as open-source Truck or a licensed Parasolid or ACIS kernel, where they represent the same operation. Track failure rate, latency, memory, persistent reference survival, interchange fidelity, license and maintenance effort. Mirum's review, artifact identity and revision contracts remain authoritative.

This recommendation is available for the decision review. Formal Phase 3 sequencing still places F11 after the F10 release gate.
